# Repository instructions

- Open items and follow-ups are GitHub issues on the private repo skolia-io/tracking (`gh issue list -R skolia-io/tracking`, `gh issue create -R skolia-io/tracking -t … -b … -l …`). A PR that finishes one says so in its description, `Closes skolia-io/tracking#N` (or `Fixes`, `Resolves`), so merging it closes the issue. git-bug is no longer used.
- A pull request's title is a conventional commit, `type(scope)?: description` (feat, fix, perf, refactor, docs, test, build, ci, chore, revert), since it becomes the squashed commit on main; pr-title.yml checks it. The description is a lowercase verb phrase saying what changes: `feat: show the word type on recognition cards`.
- Start each piece of work in a new git worktree, `~/dev/skolia-<name>` beside this checkout (`git worktree add ../skolia-<name> -b <branch> origin/main`), never in this checkout.
- Keep staging as close to production as possible. Enable every production feature in staging too, with environment-specific resources and credentials.
- main moves quickly. Fetch and branch from `origin/main`, and rebase before pushing more work onto an open PR.
- After pushing to a PR, watch its CI (`gh pr checks <N> --watch`, in the background) until every job has finished, the preview's deploy and e2e included, and fix what fails. A PR isn't done until CI passes.
- `just fmt` formats everything (Oxfmt for TypeScript, JSON and Svelte; ruff; terraform fmt), and `just check` runs the lints of CI's check jobs: the format checks, Oxlint, ruff's lints, tsc, svelte-check, pyright, redocly's lint of api/openapi.json and terraform validate. CI runs `just check-project <project>`, a project's lints and tests, for each workspace package, analysis and terraform whose key changed (infra/plan.py). Run `just fmt` before committing. Oxfmt and Oxlint use .oxfmtrc.json and .oxlintrc.json.
- API tests call the typed client: `client(app, headers)` (src/testing/app.ts) with `body()` and `expectStatus()` (util/responses.ts). `raw()` is only for requests the client can't express, such as malformed JSON. Don't call `app.request()` in tests; where you see one the client or `raw()` could make, rewrite it.
- Avoid stubs and mocks where possible: test against the real thing (workerd, a local D1, wrangler dev, a preview deploy). A test that stubs what it's about (a fake `wrangler` to test a deploy script) shows only that the code does what the stub assumes. When a stub seems forced, first weigh whether a test is worth having at all, or whether the real run (CI's deploy, the end-to-end tests) is the check.
- A user has roles through `role_binding` (user, role), any number of them, from the `role` lookup table, seeded with `system`; someone who signs up has none. `GET /api/me` sends them as `roles`. To add an app-supported role, seed a row in a data migration and add it to `ROLE_NAMES`; a role grants nothing until `role_permission` says so. The seeded users `system`, the e2e tests' importer (src/e2e-keys.ts), and `curated`, the curated texts' (src/sync-curated-key.ts), are bound to `system`. E2E keys are run-scoped. Curated sync replaces only its own API key id.
- What a user may do is the union of their roles' permissions: the `permission` lookup table, granted to roles in `role_permission` (D1). Code checks a permission, `hasPermission(deps, user, "unlimited-rate")` (api/src/permissions.ts, one indexed query over `role_binding` and `role_permission`), never a role's name. A new permission is a row in `permission` and its grants in `role_permission`, seeded in a data migration, and a name in `PERMISSION_NAMES` (shared/api.ts).
- Curated texts live in `curated/{lang}/*.yaml`, one text each, of a kind (api/src/curated-kinds.ts): `inline`, the text and its credits in the file. A Wolne Lektury work is vendored into one, `node api/src/vendor-wolnelektury.ts <slug> curated/pl/<name>.yaml --tag level:A2`, so the sync needs no network but the API's. Every deploy syncs them (`just sync-curated <env>`, src/sync-curated.ts). A push to main that only changes texts syncs staging alone (CI's plan, infra/plan.py, finds nothing else changed), and production gets them at the next tag. An edited text is a new document; the old one is deleted. An `inline` text marks spans Pandoc's way, `[some words]{label}` (`\[ \] \\` escape; spans nest, each label once), and `annotations:` gives each label one annotation or a list: NewAnnotation without start and end, its kind's data beside its kind (`kind: audio`, `url: …`), with YAML merge keys (`<<: *narration`) for what repeats (api/src/curated-spans.ts, curated-kinds.ts). The imported text and the offsets are the text without markup; the sync adds and removes the curated user's annotations to match.
- Tags are kind:value pairs (`level:B1`) on a user's entry for a text, at most one of each kind, set and changed only by the entry's user and seen with the entry. The `tag` table holds the ones that can be given, with a description and an order; a new tag is a row there, and `GET /api/tags` lists them, so the reader isn't written for any kind. `GET /api/documents?tag=level:A1&tag=level:B1` narrows the list: any of one kind, all of the kinds. Curated files give theirs under `tags:`; one the table lacks fails the sync, not the offline check.
- Timestamps are named for what happened, with `_at`: `added_at` columns in SQL, `addedAt` in TypeScript and the API's JSON. Not bare `added`, `imported` or `updated`.
- The full API D1 and User DO schemas are checked in under `api/schema/`; update the snapshots alongside schema changes (see DEVELOP.md).
- A pull request's preview applies its D1 migrations as they're pushed, so a migration that has been pushed is deployed: change the schema with a new migration, not by editing one, or the preview's database won't match. The user Durable Object's migrations (api/src/user/migrations) differ: on previews and locally (`MUTABLE_FINAL_USER_MIGRATION`), an edited last one is reverted with the down it was applied with and applied again, so it can be changed until it reaches main.
- `@skolia/util/sql` (util/) is a tagged template for SQL put together from parts: values become parameters, `sql.join` and nested fragments bring their own. `@skolia/util/query` is an untyped query builder (`select`, `insertInto`, `update`, `deleteFrom`, `unionAll`, `eq`, `and`, `exists`, …) that compiles to a `Sql`, for queries put together conditionally: `where` skips false conditions and adds to those a query has. A string is a column where an expression goes and a parameter where a value goes; `col()` and `lit()` cross over, and `lit()` keeps a constant in the SQL for a partial index. A fixed query stays an `sql` template. `@skolia/util/checks` has the column checks the user Durable Object's migrations share (`iso`, `isoOrNull`).
- No query reads rows in proportion to a table or an entry's rows: each one seeks an index (schema.workerd.test.ts checks the D1 document queries for SCANs). A count is kept, not counted: a column or side table that triggers update in the statement that adds or removes a row, like `user_document.annotations_count`, rather than `count(*)`.
- A row that's one of several kinds (a discriminated union: annotations, cards) is one table with a `kind` column and a `data` column, a JSON object of what the kind adds; what every kind has is columns. The database checks only that `data` is an object (`json_valid(data) AND json_type(data) = 'object'`); the zod schema checks the rest, `{ kind, data }` as a `z.discriminatedUnion` (`AnnotationContent`, `CardContent` in shared/schemas.ts), and the API sends the same shape. A new kind is a variant there, not a table. Code that differs by kind matches on `kind` with a `switch`, so a new kind is a type error where it needs a decision. A kind's field that a query looks up is an expression index, partial on the kind (`card_blank`: `(data ->> '$.documentId', data ->> '$.blankStart') WHERE kind = 'cloze'`), and queries use the expressions from one shared constant (user/queries.ts), since SQLite seeks it only if they're spelt the same.
- Dispatch on union variants exhaustively, even when there are only two. In Python use `match` with a final `case _` that calls `assert_never`. In TypeScript use `switch` with a `never` check so adding a variant fails type checking at each dispatch site.
- Don't hard-code evolvable application enums in SQL `CHECK` constraints (`lang`, `kind`, `state`, `status`, `licence`, `visibility`, etc.). Keep the column typed (`TEXT NOT NULL` when required) and validate the allowed values and variant data in Zod at the application boundary. SQLite needs a table rebuild to change an existing `CHECK`. Keep structural invariants such as JSON shape, date format, boolean encoding, numeric bounds, and tag syntax; these aren't lists of application values.
- A table alias is a word, not a letter: `entry`, `annotation`, `attribution` (or `ann`, `attr`), never `a`, `e` or `n`.
- Put code that's needed in more than one place in a util package (util/, or shared/ for API and reader types) rather than copying it. A helper that a checksummed migration uses must keep making the same SQL.
- Avoid `string` where a narrower type exists. Ids are branded types from shared/schemas.ts (`DocumentId`, `UserId`, `CardId`, `LemmaId`, `Timestamp`), parsed where they come in (a route, a URL, a test's literal) and passed as that type from then on, in the API and the reader alike, query keys and props included. Statuses and kinds are unions of literals.
- A new timestamp column is named for its event with `_at` (`added_at`, `updated_at`), and its JSON field `addedAt`, `updatedAt`. Older columns (`updated`, `created`, `imported_at`) keep their names.
- Two different things are called `Ingester`: the Durable Object in ingest/src/main.ts, which starts the container and hands it jobs, and the job loop in analysis/src/skolia_analysis/ingest/worker.py.
- The API binds the ingest Worker's `Ingester` (`INGESTER`, `script_name`) to ask where a document is in the queue. The workerd test harness has no ingest Worker, so src/testing/ingest-recorder is named `skolia-ingest` and has a stub `Ingester`.
- A PR that changes what the reader looks like has screenshots in its description, at desktop and phone widths (1280 and 390 px) where it matters. Run the reader against staging (`SKOLIA_API=https://staging.skolia.io pnpm --filter @skolia/reader dev`, where you're signed out), open a text by its link (lib/link.ts gives the word and view), and take them with Playwright: `uv run --with playwright python -I shot.py` from the scratchpad, with `playwright install chromium-headless-shell` once. Refer to them in the body as `![alt](./name.png)` and pass each file to `gh pr create` or `gh pr edit` as `--attach ./name.png`, which uploads it and rewrites the reference.
- TypeScript leans readonly and functional where it costs little: `readonly` fields and collections, values built with `map`/`flatMap`/`reduce` rather than filled in later, and objects whole when they're created rather than holding placeholders. A plain loop is fine when it reads better.
- api/src/bundle.test.ts caps the gzipped Worker bundle. CI's gzip came out about 1 KiB bigger than a local macOS build, so leave some room when raising it.
- Log through a structured logging library, never bare `console.log`/`print`: what happened as the message, and what it's about (ids, paths, counts, `ms` for timings) as fields. TypeScript uses LogTape: the Workers' `log()` (api/src/log.ts), and a script's `scriptLog()` with its main in `runScript()` (api/src/script-log.ts), which writes logfmt, or JSON Lines with `LOG_FORMAT=json`. A script's usage message and the output another program reads (SQL on stdout) aren't logs.
- To debug a deployment, read its logs and traces (Workers Observability, every Worker and environment) through the API with the read-only debug token (infra/tokens, in `pass cloudflare/skolia-io/22d39fac63e580576e28d9ed133ab62d/debug`): `POST https://api.cloudflare.com/client/v4/accounts/22d39fac63e580576e28d9ed133ab62d/workers/observability/telemetry/query` with `{"queryId":"adhoc","timeframe":{"from":<ms>,"to":<ms>},"view":"traces","limit":100,"parameters":{"filters":[{"key":"$metadata.service","operation":"eq","type":"string","value":"skolia"}]}}`. `view: "traces"` lists traces (`traceId`, `rootTransactionName` such as `GET https://skolia.io/api/me/cards/due`, `traceDurationMs`); `view: "events"` with a `$metadata.traceId` filter gives one trace's spans and logs, each span's `$metadata` holding `service`, `spanName`, `startTime`, `endTime` and `parentSpanId`. The service is the Worker's name: `skolia` (the API), `skolia-ingest`, `skolia-lexicon`, `skolia-oauth-proxy`, and staging's with `-staging`; a span's `source.deployment.environment.name` is `production` or `staging` (a preview's has none). If the token lacks a permission, add it to `debug_account_permissions` there and ask for an apply.
- Every offset into a text, stored or sent, is in UTF-16 code units, a JavaScript string index: the analysis's tokens and sentences (blob.py converts Stanza's code points), cloze cards, annotations and curated spans. Python slicing a text with them uses `utf16_slice` (blob.py). Nothing else converts.
