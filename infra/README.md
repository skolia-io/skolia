# infra

Terraform for what wrangler doesn't deploy: per environment, an R2 bucket, D1 databases (the app's, and a lexicon per language), and a queue; and once for the account (`infra/shared/`), billing usage alerts, the provider mirror, the lexicon's sources (`skolia-lexicon-sources`) and `skolia-ci`, a D1 of what CI has built and deployed (`build` and `deployment`, which only grow; `infra/skolia-ci/migrations`, applied by `just migrate-ci` after the shared apply). Three Workers are deployed with wrangler: `skolia` (reader + API, on workers.dev and skolia.io) from `api/wrangler.jsonc`, `skolia-ingest` with its containers from `ingest/wrangler.jsonc`, and the API-owned `skolia-internal` from `api/wrangler.internal.jsonc`. The internal Worker has no public route; it publishes document status for ingest through a restricted service entrypoint. It deploys after schema migrations and before ingest, with no binding back to ingest or the public API. The public API runs background data migrations on cron only after these publishers deploy. Wrangler applies their Durable Object migrations; the provider resends the first migration on every update, which Cloudflare refuses ([cloudflare/terraform-provider-cloudflare#5701](https://github.com/cloudflare/terraform-provider-cloudflare/issues/5701)).

All are on the same account. What there's one of per account (billing alerts, the provider mirror, the lexicon's sources, `skolia-ci`) is in `infra/shared/`, its own environment `shared` with its own state, `skolia-shared.tfstate`; CI's `deploy-shared` applies it from main when something a plan reads changed. `infra/tf.sh <env>` and `infra/wrangler.sh <env>` run terraform and wrangler for one environment. Each Worker’s Wrangler config names its D1 databases and wrangler looks up its id. If the name isn't there, `wrangler deploy` creates it outside Terraform, so Terraform goes first (`deploy-infra`); `d1 migrations apply` fails instead.

A new environment: add it to the checks in `tf.sh`, `wrangler.sh` and `deploy-ingest.sh` and to `var.env`, add its `env` blocks, then `infra/tf.sh <env> apply`, and deploy.

### Previews

Each pull request from a branch of this repository gets a preview, `pr-N`, deployed and end-to-end tested on every push (`ci.yml`, job `deploy-preview`). Merging needs it to pass (`ci.yml`, job `mergeable`); a fork's pull request gets none and isn't held up, and nor does one whose every deploy would match staging's (a change to docs or Markdown alone), which isn't deployed. It is on workers.dev only. Its wrangler configs are made by `infra/preview.py config pr-N` from the `env.staging` blocks, with `-pr-N` names, its workers.dev URL and ingest containers that sleep after 10 s idle; `deploy-infra` makes them after Terraform, and `wrangler.sh` when they're missing. They're gitignored.

Closing the pull request tears the preview down (`just teardown pr-N`, `infra/teardown.sh`): the queue's consumer, the ingest Worker, its container applications (which `wrangler delete` leaves), the skolia Worker, the bucket's objects, `terraform destroy`, then the state object. Each step skips what's already gone, so it can be run again. Every night `sweep.yml` runs `infra/sweep.sh`, which finds previews by their resources' and state's names, tears down those whose pull request isn't open, and fails if any are left; `infra/sweep.sh -n` lists them without tearing them down.

Repo writers can post `/preview teardown` as a standalone comment on an open same-repo PR to delete its preview and data. `/preview reset` also reruns CI for the current PR revision. Reset refuses before deleting if there is no eligible CI run; normal CI may skip recreating a preview that would match staging. Wait for PR CI to finish before either command, and avoid pushing or closing the PR while it runs.

Google sends a sign-in only to a redirect URI its client lists exactly, so a preview's own URL can't be one. Previews sign in through the OAuth proxy instead, `skolia-oauth-proxy` at https://oauth-proxy.skolia.io (`oauth-proxy/`, a package of its own on the API's better-auth, the workspace catalog's), the `skolia-preview` client's redirect URI, with Better Auth's oAuthProxy plugin: a preview's sign-in sends Google to the proxy with the preview's state, encrypted with `OAUTH_PROXY_SECRET`, which the proxy and the previews share; the proxy exchanges Google's code and redirects to the preview with the profile, encrypted too; and the preview makes the user and session in its own D1. The proxy keeps nothing, answers only `/api/auth/callback/google`, and redirects only to a preview's origin (`PREVIEWS`). `infra/preview.py` gives each preview its URL, `OAUTH_PROXY_URL`. It's deployed from main (`ci.yml`, job `deploy-oauth-proxy`; `just deploy-oauth-proxy`), so a pull request that changes how it works signs in on its preview only once it's merged. Anyone with a Google account can sign in on a preview, and import.

### Container usage

`infra/container-usage.py [--since DATE] [--until DATE]` prints the containers' memory use (GiB-seconds, what Cloudflare bills; 25 GiB-hours a month are free) per environment and per day, by default for this month. Torn-down previews show as `deleted`. Most of it is deploys': each one's end-to-end tests and curated sync start a container per language, which stays up `SLEEP_AFTER` (`ingest/src/main.ts`) once idle.

## Deploy

A push to main deploys staging and runs the API end-to-end tests (`e2e/tests/`). Production and previews run the same suite. After verifying the deployed version, the runner provisions temporary credentials in D1 in one batch. A private import runs in each language while auth, lexicon and isolated card journeys run against the same API. The logs report version readiness, credential setup, import, ingest queue and processing times, observed readiness and verification. The suite removes its private document entries and deletes its own credentials and fixture users on exit. Keys expire after an hour if cleanup is interrupted. `deploy-web` waits for `load-lexicon`, since the journeys read the lexicon. After `deploy-web`, two jobs run side by side: `e2e`, the tests, and `sync-curated` (`sync-curated.yml`), where `just sync-curated <env>` makes the library's curated texts match `curated/`, fetching those whose kind names a source (`api/src/curated-kinds.ts`): it imports them publicly as the curated user, a system user, with its own key (`api/src/sync-curated-key.ts`), updates their titles and licences, and deletes the curated user's texts that are no longer there (`just sync-curated <env> --check` lists what it would do). Pushing a `v*` tag on a commit in main deploys staging, then production once staging passes (`git tag v0.1.0 && git push origin v0.1.0`; `.github/workflows/ci.yml`, `deploy.yml`). The internal Worker is deployed before ingest, and the ingest Worker before the skolia Worker, since it has the workflow the skolia Worker starts runs of: an API that starts a new kind of run never goes live before the ingest that handles it. Rolling back goes the other way: the skolia Worker first. Deploys don't wait for `check`: a preview is up while it runs, and main and tags passed it in the merge queue. Each deploy starts with a plan (`infra/plan.py`, `deploy.yml`) that skips what's current. `infra/plan.py` has a dependency graph, as in ci-planner, with Nix hashes where ci-planner had git trees. Its nodes are paths and Nix packages, and its edges are read from the manifests a path has: a `package.json`'s workspace dependencies (and the lock files), a Terraform root's local modules (and the terraform and scripts that run it), and each Worker's `wrangler.jsonc` for the D1 migrations it applies; `STATIC` holds the few no manifest says. A Nix package has no edges: its out path covers what it's built from. A node's checksum is a hash of its version (its files' Nix source, without Markdown; a Terraform root's `*.tf` and lock file; a Nix package's out path; the screenshots' LFS baselines' git tree) and its dependencies' checksums, so a change reaches what's downstream of it and nothing else. The targets (`targets()`) are CI's jobs: each builds on nodes, tests nodes, or runs against other targets once deployed, and its key hashes theirs. The skolia Worker's source leaves out tests, so a change to a test reruns the checks but deploys nothing. `plan.py graph` prints each target's key and edges and the nodes they reach, and `plan.py graph --dot | dot -Tsvg > plan.svg` draws them. `skolia-ci`, an account-wide D1 (`infra/shared/ci.tf`, `infra/skolia-ci/migrations`, applied by `just migrate-ci`), keeps two tables that only grow. `build` has a row for each build and check, done once for every environment: each language's image (in the registry), the skolia Worker (`skolia-worker`, in Cachix), and each project's check, the screenshots' and each `terraform plan`'s pass. `deployment` has a row for each deployment to an environment: Terraform and the migrations, the internal Worker, the ingest Worker, the lexicon, the skolia Worker, the end-to-end tests (on the five before) and the curated sync (on `curated/` and the skolia Worker); what an environment serves is each one's last row. The checks, the tests and the sync add theirs only once they pass, so they run again only after what they read changes, or after a failure, and `mergeable` takes a pass from an earlier run against the same keys (`current`). A curated text that names a source (`wolnelektury`) isn't synced again when only the source changes. The scripts that build and deploy add the rows (`deploy-ingest.sh`, `just load-lexicon`, `just deploy-web`, `build-web`), by hand too, and the plan skips a build whose key has a row and a deployment whose key is the environment's last. A preview's teardown adds a row with no key for each package. The skolia Worker is built by `build-web` into Cachix while the jobs before `deploy-web` run, and `deploy-web` uploads that build. The version it serves is the tag at HEAD, or else the last tag and the build's hash (`infra/plan.py version`), not a commit, so a skipped deploy serves what a new one would, and that's what the end-to-end tests expect. It's a var (`VERSION`), not in the bundle. When `pnpm-lock.yaml` changes, so does `skolia-worker`'s `pnpmDeps` hash: set it to `""` and `nix build .#skolia-worker` reports the new one. A change to the deploy scripts alone (the justfile, `infra/` beyond `tf.sh` and `wrangler.sh`) deploys nothing, and the keys don't see secrets: after changing one in GitHub, deploy by hand (`just deploy-web <env>`). One deploy of an environment runs at a time, so no older deploy lands between the plan and what it skipped. A newer push to a pull request or to main cancels the run before it, once any step that changes what's deployed (Terraform, migrations, a Worker's deploy, a teardown) has finished (`.github/uninterruptible.sh`); GitHub kills such a step 5 minutes after the cancel if it's still running. Pull requests get a `terraform plan` for staging and production (Terraform's resources only, not the Workers). GitHub needs:

- variable `CLOUDFLARE_ACCOUNT_ID`
- secrets `CLOUDFLARE_API_TOKEN` (the deploy token above), `ALERT_EMAIL`, `CACHIX_AUTH_TOKEN`
- in the `staging` and `production` environments, secrets `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (the OAuth clients above)
- in the `preview` and `oauth-proxy` environments, the `skolia-preview` client's `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, and the same `OAUTH_PROXY_SECRET`
- environments `staging`, `production`, `preview` (every pull request's) and `oauth-proxy`

Not every change deploys. CI's first job, `plan` (`infra/plan.py plan`), decides what every other job does, from the keys above: the checks (one per project, `check-<project>`: each workspace package, `analysis` and `terraform`; the screenshots; each environment's `terraform plan`) whose keys haven't passed, and for each environment the run deploys (a pull request's preview; staging and `shared`, `infra/shared/` and the OAuth proxy, from main; staging and production from a tag), the deploys whose keys it doesn't have and the builds they need. So a change to docs or Markdown alone runs nothing after `plan`; a change to curated texts alone runs `check-api` and the curated sync; and `mirror-providers` runs only when something needs Terraform. A skipped job counts as passing, so the queue requires `mergeable`, not the checks: it fails when a check the plan said was needed didn't pass.

CI installs Terraform's providers from the public R2 bucket `skolia-tf-providers` (`infra/shared/mirror.tf`) through `infra/terraformrc`, since the registry sends Terraform to GitHub's releases, which time out for unauthenticated requests at times. CI's `mirror-providers` job (`infra/mirror-providers.py`, also `just mirror-providers`) runs before `check` and adds whatever in `.terraform.lock.hcl` the mirror is missing, downloading GitHub's zips with a token; a zip whose hash isn't in the lock file is refused, and the lock file's hashes check what CI installs.

These, and `main`'s ruleset (pull requests only, through a merge queue that requires CI's `mergeable` and `pr-title` jobs), are managed in Terraform in the dotfiles (`~/.dotfiles/terraform/github`), from `pass`.

By hand, with the credentials above, the same tasks CI runs:

```fish
just plan staging
just apply shared               # billing alerts, provider mirror, lexicon sources, skolia-ci
just migrate-ci                 # skolia-ci's tables
just deploy staging              # deploy-infra, deploy-ingest and deploy-web, in order; not load-lexicon
just deploy-infra staging        # terraform apply, D1 migrations
just deploy-ingest staging       # build, push and deploy the containers
just load-lexicon staging        # the flashcards' lexicon into D1, if its version is new; a preview gets each language's entries for wordfreq's 3,000 most common words
just deploy-web staging          # the skolia Worker (reader and API)
just e2e staging
just teardown pr-12              # previews only
```

`deploy-ingest` builds one image per language with Nix (`analysis/flake.nix`, `x86_64-linux`; on a Mac, Determinate Nix's Linux builder, DEVELOP.md): the models (fixed-output, pinned by hash), the venv from `uv.lock` (uv2nix), the lexicon from the inputs pinned in `inputs.sha256` (`fetch_inputs.sh <lang>` puts them in the store), and one layer per model, one for PyTorch, one for the other dependencies and one for the lexicon, as Cloudflare's registry times out committing a single 3 GB layer. Its tag is its Nix hash, which `nix eval` gives without building anything. It runs the parser check (`checks.x86_64-linux.{lang}`, which fails if the parser needs a model file the image doesn't have), pushes the image with skopeo (nix2container) with the credentials `wrangler containers push` would use, retrying, and sending only the layers the registry doesn't have, and deploys the ingest Worker with each image, pinned by the digest the registry gives (`skopeo inspect`), in place of `analysis/image/Dockerfile` under its language's name in the container's `images`. The container uses the `durable_object` scheduling policy: the ingest Worker hands each job to the `Ingester` named after its language's image, which starts a container with that image, so a deploy that changes an image sends new jobs to a new container while the old one finishes its jobs and stops. In CI each missing image is built on its own runner, beside `deploy-infra` (`deploy-ingest.sh build <lang>`), pulling from and pushing to the `andyyu2004` Cachix cache everything but the models (`analysis#cacheable-{lang}`), which it downloads again when an image changes; one job then deploys the ingest Worker with all of them (`deploy-ingest.sh <env> deploy`).

For a warm-up experiment, set the GitHub Actions variable `WARM_INGEST` to `true` in the target environment. When a web deploy and e2e are both planned, CI queues a warm-up just before the web upload. You can also queue one manually with `just warm-ingest <env>` after deploying ingest. A warmed container gets up to three minutes to receive its first job, then uses its normal idle timeout.

A new language: its models and lexicon in `analysis/flake.nix`, an image named after it in `images` in `ingest/wrangler.jsonc` (both environments), the language in `langs` in `deploy-ingest.sh` and `load_images.sh`, in `LANGS` in `infra/plan.py` and in `langs` in the `justfile`, `local.langs` in `infra/variables.tf`, a `LEXICON_{LANG}` binding in `lexicon/wrangler.jsonc` (both environments), its Wiktionary section and sources in `lexicon/src/licence.ts`, and its inputs in `fetch_inputs.sh`.
